# Фабрика Board + Herdr (`--runtime hc`)

Этот репозиторий — актуальный исходник фабрики. Board хранит задачи, зависимости и квитанции; Herdr Core (`hc`) исполняет изолированных воркеров (`devin`, `pi`, `agy`) в отдельных worktree; Git SHA и детерминированные гейты подтверждают результат.

## Как работать

1. Уточни результат и критерий в **одной** карточке Board; бери только согласованный scope. Готовая задача — явная граница между обсуждением и исполнением.
2. Работа — в feature-worktree изолированного слота. Один писатель на рабочую копию; перед новым worktree/сборкой пройди дисковый preflight. Сдача указывает карточку, попытку и точный чистый SHA со всеми нужными файлами.
3. Scope Fence — жёсткая граница: изменяй только пути из метки `allowed_paths` карточки; всё остальное — read-only, даже если заметил дефект. Посторонние находки передавай в заметках сдачи, не правя чужое.
4. Проведи проверки из доверенного профиля и независимое кросс-семейное L2-ревью того же чистого SHA. Исполнитель не принимает свою работу; завершение хода воркера не доказывает сдачу/приёмку.
5. Вся кодовая работа — только через принятый контроллер фабрики (`board_pipeline/run-isolated.mjs` / `daemon.mjs`, запуск — `ops/factory-run.mjs` с `--runtime hc`). Запуск исполнителей в обход контроллера запрещён: он не несёт закреплённые входы, гейты и конверт сдачи.
6. Одна задача/веха — один свежий чистый контекст лида. По закрытии итог фиксируется в Board и Project Memory; следующая задача стартует новым чистым лидом строго по Board, Project Memory и Owner Decision Ledger.
7. Политика выпуска отдельно от ревью: действующие branch checks обязательны, выпуск/мердж/push/CI и запись в рабочие данные — только по допуску владельца. Если нужен владелец — один конкретный вопрос с действием и доказательством.

## Куда смотреть

- **Вход лида: идея, grill, to-spec, вопрос владельцу** → [стандарт intake: сверка решений владельца и спека](docs/lead-intake.md). Применимые решения сверяются до вопроса и передаются в согласованном поручении, без доступа воркера к базе.
- **Реализация или исправление пайплайна** → [порядок, интерфейсы и сценарии отказа](docs/implementation-plan.md). Начинай следующий этап только после согласования scope.
- **Проверка установленной среды** → `npm run doctor`; тесты → `npm test` (на worker/dev-хосте с достаточной RAM). Тяжёлый стенд — отдельно по preflight.
- **Правки локальной обвязки** → `ops/local/` — версия исходников. Действующая Board и её данные находятся вне Git. Подключение только явно; не подменять установленный runtime по ходу тестов.
- **Почему устроено так** → [происхождение, подтверждённый статус и исследование](docs/STATUS.md).

## Границы

Одна очередь — Board. Старые `stg`, `factory/book.py`, диспетчер и их worktree — архив, не источник новых задач. Не сбрасывай и не перемещай чужую работу. Рабочие БД, токены, сессии исполнителей, профили браузера и build-артефакты остаются вне репозитория. Код от воркера не получает полномочия из текста карточки или сдачи.
