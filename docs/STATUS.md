# Статус Darkfactory v1.2.0: Board + Herdr (`--runtime hc`)

**Состояние кода v1.2.0:** фабрика работает на Herdr Core без BB. Сборка кандидата не меняет установленный runtime, конфигурацию Board или состояние слотов; приёмка SHA и решение о живом выпуске независимы.

## Подтверждённый базлайн

| Срез | Реализовано и проверяется |
|---|---|
| BB-free исполнение | Herdr Core (`--runtime hc`) запускает `devin`, `pi`, `agy` и `zcode`. В v1.2.0 доступны zcode с GLM-5.3-Flash по Start Plan и воркеры Devin Fusion. Идентификатор `df-<task>-<hash>` привязан к попытке; блокировка worktree допускает только одного писателя. |
| Crash-Resumable Worker | Прерванная попытка возобновляется по сохранённому состоянию слота и session id без потери контекста исполнения; повторный запуск не плодит дубликаты воркеров. |
| Многослотовая оркестрация | `cloud-worker` (Spot VM) несёт четыре параллельных изолированных слота `--runtime hc`, каждый со своим feature-worktree, state и inbox daemon'а. Дисковый preflight и Resource Steward предшествуют новой резервации. |
| Hardened L1/L2 Docker | L1-проверки выполняются в hardened Docker-песочнице: `network: none`, read-only кандидат, непривилегированный пользователь `65534:65534`, аттестация образа по OCI-метке `df.l1.profile`. L2-стадия изолирована от среды воркера и видит только закреплённые входы ревью. |
| Гейты целостности | `cmd-guard` (тиры CRITICAL/ORDINARY деструктивных команд), `tamper-gate` (статический разбор diff: удаление тестов, skip/only, ослабление проверок, подмена runner'а, секреты), `origin-guard` (Host/Origin против DNS-rebinding/CSRF, строгий CSP, санитизация терминального вывода). |
| Scope Fence | Метка `allowed_paths` карточки задаёт жёсткий список путей, которые воркер вправе менять; доверенный гейт сверяет diff кандидата и возвращает `scope_fence_violation` на любое расхождение. |
| Кросс-семейное L2-ревью (Review Panels) | В динамическом режиме риск изменения определяет, достаточно ли одного критика или нужна панель. Проверяется точный SHA; при выборе критиков исключаются семейства исполнителя (включая оба семейства Fusion) и арбитра. За ревью можно наблюдать во вкладках L2 в Herdr. |
| Control Room / Herdr Action Gate | Веб-пульт и `df-herd` показывают события контроллеров, состояние Board и слотов. По умолчанию пульт работает на чтение; отдельно включаемый Herdr Action Gate проверяет полномочия оператора и ведёт журнал действий над `hc`-сессиями. |
| FinOps | Декларативный read-only реестр ресурсов, бюджетов и кредитов; живой статус и минуты Spot VM читаются из usage-журнала `cloud-worker`. Ошибка конфигурации не роняет агрегатор. |
| Multi-repo L1-профили | Реестр доверенных профилей `node` и `python-node` — единый источник правды выбора среды проверок; дефолт определяется репозиторием, неизвестное имя — fail-closed отказ до любого вызова docker/Board. |
| Merge Queue | Очередь принимает проверенный SHA в интеграционную ветку, сверяя её ожидаемую вершину. После перебазирования нужна повторная L1-проверка; для защищённой ветки обязателен отдельный допуск владельца. |
| Scope-Lock Scheduler | До резервации слота планировщик сверяет `allowed_paths` задач одного репозитория. Пересекающиеся области не исполняются параллельно; задача без указанной области занимает весь репозиторий. |
| Unified Owner Decision Ledger | Единый реестр SQLite разделяет предложения и действующие решения: предложение становится решением только после явного одобрения владельцем. |
| Session Archive DB | Локальный архив SQLite хранит сессии исполнителей и поддерживает полнотекстовый поиск; для гибридного поиска векторный адаптер подключается отдельно. |
| Unified Fleet Dispatcher + CI Healer | Диспетчер распределяет слоты между проектами по доступным CPU и памяти. При явном включении CI Healer создаёт в канале проекта карточку на исправление сбоя CI, но не перезапускает CI и не меняет ветку. |
| Owner Twin / Teamlead | Owner Twin отвечает на подходящий вопрос со ссылкой на одобренное решение владельца; при неоднозначности передаёт вопрос владельцу. В управляемом режиме Teamlead принимает запросы проекта через его канал. |
| Валидация трасс TLA+ | По журналу `events.ndjson` проверяются наблюдаемые инварианты протокола контроллера. Проверка трассы не доказывает свойства, которых нет в журнале, и не заменяет допуск выпуска. |

В daemon и foreground используется один путь выполнения тика. После закрытия или блокировки карточки daemon пишет итог перед очисткой активной попытки; следующая карточка получает отдельные счётчики. Типизированный `ReleaseReceipt` остаётся неизменным для проверки digest; телеметрия выпуска остаётся в приватном журнале.

## Что доказывают проверки

- `npm test` — детерминированный регрессионный набор модулей и стыков Darkfactory v1.2.0: контроллер, worker runtime `hc`, гейты, control-room, обвязка. Актуальный состав задаётся `scripts.test` в `package.json`; прогонять на worker/dev-хосте с достаточной RAM, не на малом control-plane.
- `npm run test:integration` — локальная Board, файловые и HTTP-эффекты, Docker-проверки и маршрутизация на синтетических данных.
- `npm run test:tla` — проверка модели протокола контроллера в TLC, мутантов и трасс. Это проверка инвариантов модели, а не аттестация живого выпуска.
- `npm run doctor` — отдельная read-only сверка установленного окружения и рантаймов. Сетевые модельные прогоны отделены от детерминированных проверок и включаются явно.

## Граница запуска

Действуют [план реализации](implementation-plan.md), отдельный допуск пилота и отдельная авторизация выпуска. Подключение daemon, слотов, production-доступа или публичного экспорта требует своего разрешения владельца. Рабочие данные, учётные данные и сессии не входят в репозиторий. Исторические документы эпохи BB — [пилот v1](board-pipeline-v1.md) и отчёты ранних этапов — не являются инструкцией для эксплуатации этого кандидата.
