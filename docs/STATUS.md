В daemon и foreground используется один путь выполнения тика. После закрытия или блокировки карточки в очереди daemon пишет итог перед очисткой активной попытки; следующая карточка получает отдельные счётчики. Обычная квитанция `verified` может содержать компактную сводку. Типизированный `ReleaseReceipt` остаётся неизменным для проверки digest после native complete; телеметрия выпуска остаётся в приватном журнале.

## Что доказывают проверки

- `npm test` — детерминированные проверки модулей и стыков, включая daemon CLI с временной Board и имитацией BB. Тест с двумя карточками проверяет утверждённый intake и два независимых итоговых отчёта.
- `npm run test:integration` — локальная Board, файловые и HTTP-эффекты, Docker-проверки и маршрутизация на синтетических данных. Проверяются неизменная квитанция T4 при включённой телеметрии и повтор инцидента P2.2 после потери подтверждения.
- `npm run test:tla` — базовая модель контроллера и пять парных мутантов. Это проверка инвариантов модели, а не аттестация живого выпуска.
- `npm run doctor` — отдельная read-only сверка установленного окружения. Сетевые модельные прогоны из [профиля T1](vs2-t1-review.md) отделены от детерминированных проверок.

## Граница запуска

Действуют [план реализации](implementation-plan.md), отдельный допуск пилота и отдельная авторизация выпуска. P1.1 и T4 работают в выделенном изолированном контуре; заявлять production-автономию по их тестам нельзя. Подключение daemon, наблюдателя, Resource Steward, production-доступа или публичного экспорта требует своего разрешения. Рабочие данные, учётные данные и сессии не входят в репозиторий. Исторический [пилот v1](board-pipeline-v1.md) не является инструкцией для эксплуатации этого кандидата. Для отдельно допущенного живого E2E нужен [операторский файл фикстуры](vs1-e2e.md).
