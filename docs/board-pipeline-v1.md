# Фабрика вокруг Vercel Board — v1

**Цель.** Одна задача должна пройти от поручения до проверенного результата без чтения логов BB владельцем. Пилот — запуск автопроверок и активный список в MO Tracker. Выкладка не входит.

## 1. Границы и роли

Board 0.54.0 — единственная очередь: карточка, зависимости `needs`, состояние, владелец, результат. BB — запуск, worktree и идентичность исполнителя. Git — проверяемая версия. Поведение приёмки — отдельный локальный шлюз; не дописывать старую `factory/book.py`, не запускать `df-dispatcher` и не переносить backlog. Один worktree на самостоятельный результат. Не вводить автоматические запуски по постам, общую квоту итераций, TLA+, синхронизацию или новую службу в v1.

Лид принимает поручение, задаёт критерий, даёт одну карточку и назначает работу. Исполнитель (по умолчанию Devin `acp-devin` / `swe-2-high`) сдаёт артефакт; не принимает собственную работу. Локальные команды назначает профиль, не текст от воркера. Независимое ревью в рабочем режиме — существующий `board-review.mjs`, Pi `openai/gpt-6.2-sol`, `medium`; принимать только фактическую квитанцию на тот же SHA. Учётные записи под одним UID не являются sandbox; не утверждать, что прямые записи уже невозможно обойти. Выпуск/мердж, пуш, PR, CI, запись в рабочие БД, доступ к работам студентов, изменение оценок и платные новые сервисы не входят. В этом запуске эксперименты — только изолированная доска и синтетика.

## 2. Контракт приёмки

Явная сдача JSON: `task_id`, `worker_thread_id`, `base_sha`, полный `candidate_sha`, `worktree`, `check_profile`. Обязательное подтверждение границы: зарегистрированный репозиторий/ветка, base предок кандидата, реальный `HEAD`, чистый индекс и отсутствие незакоммиченных/неотслеживаемых входов; профиль выбирается из доверенной конфигурации. Не подхватывать shell или команды из сдачи; доставка файлов входит в commit. Тесты видят этот SHA, не случайное содержимое рабочего каталога. Для shell worktree сам по себе не изоляция: боевые данные/секреты не монтировать, сеть не использовать для локальных проверок. Изолированный пилот проверяет эти предпосылки.

Обработка: `submit → local_checks → review → completed | blocked`. Board нативным `claim` удерживает карточку, его epoch защищает от старой сдачи. Стадии и квитанции заводятся от `task_id + candidate_sha + policy_version`, не как вторая очередь. `REVIEW_BLOCKED`, ошибка локальной команды, провайдер не совпал, нет свидетельства или был отказ — не `completed`. Сохраняем причину и следующий ход. `complete` допускается только при зелёном наборе и подтверждённом `REVIEW_OK` того же SHA. При необходимости продуктовых эвалов они часть профиля, не замена тестов. `exit 0` самого запуска BB или статус `idle` — не приёмка. Операции идентичны при повторе; после аварийного неопределённого внешнего вызова сверяем факт, не запускаем повтор вслепую. Не принимать результат предыдущего epoch/другого SHA.

## 3. Задачи и последовательность

| Код | Задача | Приёмка |
|---|---|---|
| F1 | Детерминированное ядро сдачи/приёмки в `board_pipeline/`: строгий контракт, сохранение квитанций, маленькие интерфейсы Board/runner/review | `node --test board_pipeline/*.test.mjs`: корректная зелёная сдача; красные тесты не запускают ревью; неправильная/непроверенная модель, дрейф SHA, грязный снимок, повтор и авария не закрывают карточку. Без правок старой фабрики |
| F2 | Один локальный запуск через нативную Board: read/claim/settle; профиль проверок и адаптер ревью; инструкция эксплуатации | Изолированная Board: реальная карточка становится `completed` по одной принятой сдаче; другой сценарий остаётся `blocked` с причиной; потерянный claim не завершает карточку. Если реальный BB-провайдер недоступен, отдельно пометить границу заглушки, не объявлять полный E2E |
| P1 | Tracker: воспроизвести расхождение счётчика и запуска, затем исправить совместно с фильтром активных работ | Синтетика, отдельный worktree от фактического local `dev`; критерии ниже. Сдача — Git SHA + логи; принять через F2, а не руками выставлять зелёный статус |

F1 → F2 → приёмка P1. Разведка и реализация P1 могут идти параллельно в другом worktree, но доказательство пилота проходит новый контур. Сквозной запуск на действующей доске, реальных данных или с интеграциями не подменяет изолированный пилот и требует отдельной явной авторизации.

## 4. Пилот P1: автопроверки Tracker

На скриншоте `9` раскладывается как `1 comment + 4 transcribe + 4 transcribe`; нижняя таблица показывает прошлый снимок `199` и ошибку `mode not supported`. Это три разных факта, не подтверждение общей причины. Пустая ячейка или значок в журнале сами по себе не доказывают, что текущая копия работы готова к автопроверке. [VERIFY] на синтетике: что теряется из-за версии работы, no_autocheck, статуса, неполного анализа автора, отсутствия теории, сбоя стадии или расхождения выбора области. Уже сохранённые баллы и работы ручной проверки не переоткрывать.

- **Совпадение предварительного списка и запуска.** В одном и том же наборе версий и фильтров отображаем количество реально готовых к запуску работ и проверяем точное совпадение ID с запуском (не только сумму). Списки очереди и исключений не должны строиться на несогласованных правилах. Сохранить последнюю версию, `no_autocheck`, фильтры, предохранитель отсутствующей теории и запрет подмены точечного `submission_ids` массовой областью. Если работы нельзя запустить, пользователь видит причину и число, а не «ничего не совпало». Не включать автоматический ретрай постоянного `mode not supported` и не повторять неизменившийся полный запуск.
- **Активный прогон.** В основном списке текущего прогона показывать **только работы, у которых сейчас выполняется стадия**. Ожидание, завершение и ручные блоки — счётчиками; при отсутствии активных работ понятное пустое состояние. Общий знаменатель прогресса — состав этого прогона, не длина видимого списка. По завершении сохранять итог и доступ к ошибкам, но не подмешивать полный backlog в активный список. Устаревший snapshot не оживляет законченный прогон.
- **Приёмка.** Синтетический набор с >9 работами: разные ДЗ/статусы, закрытые, непригодные, повторы и ошибки различаются. Интеграционный тест `preflight → start → замороженный набор`; тест переходов активного списка; браузер на изолированном локальном Tracker с синтетикой. Тесты/линт/типизация/сборка только по изменённым границам. Где запуск не состоялся — `not run` с причиной; не запускать существующий MO Tracker и оплачиваемые модели. Если основной дефект не воспроизводится без реальных данных, поставку ограничить наблюдаемым воспроизведённым расхождением и пояснить, какие обезличенные счётчики нужны для диагноза снимка.

## 5. Запуск оператором

Команда `node board_pipeline/submit.mjs --execute --handoff FILE --policy FILE --journal DIR` не выбирает Board, worktree или проверки по умолчанию. `DIR` — отдельный каталог с mode `0700`. Операторский JSON вне worktree задаёт `version`, `boardUrl` (явный loopback `/api/board`), `channel`, `reviewGate` (абсолютный путь проверенного `board-review.mjs`), необязательный `reviewPrompt` для вызова `launch` только после тестов и `profiles`. Для каждого профиля: точные `task`, `worker`, `worktree`, `branch`, `base`, `review: {provider: "openai", model: "gpt-6.2-sol", reasoningLevel: "medium"}`, `checks` — непустой список `{image, argv, cwd, timeoutMs, mounts?, env?}`. Образы только локальные `sha256:…`, runner — только rootless Docker без сети. Сторонний профиль проверки или команду из handoff шлюз не принимает. Если `reviewPrompt` нет, используется уже существующая квитанция; сам по себе неудавшийся запрос не запускает повтор.

Запуск не обслуживает очередь фоном. Изолированные проверки `node --test board_pipeline/*.test.mjs` используют установленный SDK из `~/.local/share/vercel-board` и существующий Node-образ Docker. Синтетический интеграционный тест использует настоящий Board и Git, реальный офлайн-runner и явно обозначенную заглушку квитанции: это не доказательство фактического BB-маршрута.
