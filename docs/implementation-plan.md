# Board + BB: от поручения до проверенного выпуска

**Статус:** план реализации; живой маршрут ещё не включён. **База:** импорт `eae2f73`, `board_pipeline/`; P0.1 реализован локально; локальная Vercel Board `0.54.0`, BB. **Источники:** [разбор Puh/Eve/Anthropic/OpenAI](/home/mydum/.bb/thread-storage/thr_45h5ewmiwp/factory-autonomy-research.md), [спека и журнал v1](board-pipeline-v1.md), [квитанция пилота Tracker](/home/mydum/.bb/thread-storage/thr_45h5ewmiwp/board-v1-pilot-evidence/board-result.json).

## 0. Что хотим доказать

**Одного поручения достаточно.** Владелец видит в карточке результат или один вопрос, ответ на который действительно нужен. Система сама проводит работу через повтор после красной проверки, приёмку и согласованный способ выпуска. Проверить не только зелёную прямую, но и зависший claim, повтор события, потерянный ответ внешнего API и реальное продолжение после ответа владельца.

Уже доказано: вручную поданный SHA → изолированные проверки → фактическое независимое Pi/Sol-ревью → `completed`/`blocked` на изолированной Board. Не доказано: автоматический захват готовой задачи, возврат воркеру, возобновление по подтверждённому ответу и выпуск новым контуром. **Не менять само определение «сделано»:** для `finish=verified` достаточно проверенного SHA; для `finish=deployed` задача не `completed`, пока не подтверждены выкладка и проверка работающей версии.

**P0** — приёмка в уже удерживаемой попытке + автоматический запуск и исправление. **P1** — один вопрос, подтверждённый ответ и выпуск. **P2** — осторожное подключение действующей доски и наблюдений об инцидентах. Рубежи имеют отдельную приёмку: успешный P0 не называется автоматической выкладкой.

## 1. Схема работы

До готовности карточки лид применяет [стандарт intake](lead-intake.md): сверяет решения владельца перед grill и to-spec и переносит допустимые выписки в согласованную спеку.

```text
Владелец пишет напрямую лиду или в общий вход, без обязательных тегов
    → краткое поручение или спека; результат, проверка, границы, риск, finish
    → одна карточка Board; needs и доверенный маршрут определены заранее
    → готовая карточка (ready) в разрешённом канале и с разрешённой меткой
    → контроллер берёт native claim, записывает epoch и запускает одного BB-воркера
    → воркер сдаёт точный commit SHA
    → проверки на чистом снимке → независимое ревью по тому же SHA
        ├─ исправимый дефект → тот же воркер получает доказательство → новый SHA ↺
        ├─ проблема среды / неизвестный эффект → конкретный операционный стоп
        └─ зелёный кандидат
              ├─ finish=verified → completed с квитанцией
              └─ finish=deployed → артефакт с digest, цель, проверка рисков и откат
                    ├─ нужен допуск → один вопрос → подтверждённый ответ ↺
                    └─ разрешено → выкладка → версия + smoke на цели → completed
                                         └─ красный smoke → разрешённый откат или стоп

На любой стадии продуктовая развилка → сверка согласованных решений → один вопрос, если развилка остаётся открытой.
После выпуска: проверенное наблюдение → один дедуплицированный инцидент → тот же вход.
```

### 1.1. Что видит владелец

| Сценарий | Действие фабрики | Что видно на карточке |
|---|---|---|
| Обычная локальная правка | Краткий результат + критерий; запуск без пересылки лида | Кто работает, что проверено, финальный SHA |
| Тест красный или ревью дало конкретное замечание | Отправить контрпример назначенному воркеру, не будить владельца | `claimed`, фаза «исправление», ссылка на тест и SHA |
| Воркер указывает на неоднозначность продукта | Подтвердить, что это реальная развилка, а не незнание репозитория. Сформулировать варианты и рекомендацию | `blocked` с одним вопросом, ID вопроса, кто отвечает и что разблокирует |
| Не хватает ресурса, пропала квитанция, невозможно доказать состояние BB | Стоп без слепого ретрая; read-only сверка или заранее разрешённая механическая проверка | Конкретная причина, следующий ответственный и безопасный шаг |
| Кандидат прошёл, выпуск разрешён | Продвинуть проверенный артефакт существующим путём и проверить его на цели | SHA, digest, цель, факт выкладки, smoke и результат |
| На выпуск нужен владелец | Всё подготовить заранее; запросить одно определённое действие | `blocked` с кандидатом, целью, риском, доказательствами, откатом и точным запросом допуска |
| Регрессия после выпуска | Зафиксировать версию, симптом и воспроизведение; создать или обновить один инцидент | Карточка инцидента ведёт к доказательству; не поток пересказов |

### 1.2. Роли и канал

- **Владелец** задаёт результат, отвечает на настоящие продуктовые вопросы, подтверждает защищённое действие там, где это требует политика. Не назначает воркеров и не пересылает логи.
- **Предметный лид** уточняет критерии, безопасную границу, зависимости и маршрут только когда нужно. Для простой работы достаточно короткого поручения с исполняемым критерием. Лид не стоит на обязательном пути каждого теста, сбоя и ресабмита.
- **Локальный контроллер** — детерминированный Node-процесс, не модель. Читает Board через native claim/pull; сужает по доверенному каналу, владельцу, метке и версии политики. Нет готовых задач — нет вызовов моделей. Локальная Board не присылает wake; broad watch по переписке не нужен.
- **Исполнитель** в BB (Devin `acp-devin` / `swe-2-high` или ZCode Start GLM-5.3 Flash с `max` по разрешённому профилю) получает scope, base SHA, стенд и один worktree. Подаёт структурированную сдачу; у него нет права `complete`, claim-токена и доступа к выкладке. Другой провайдер — только по разрешённому маршруту с записанной причиной, не при каждом таймауте.
- **Проверки и ревью** задаёт доверенный профиль. Сохраняем независимое фактическое Pi/Sol `openai/gpt-6.2-sol`, `medium`, через существующий `board-review.mjs`; не принимаем саморевью воркера или строку `REVIEW_OK` из чата. Эвалы, если нужны для результата, входят в профиль наравне с тестами.
- **Выпуск** — отдельные полномочия и доверенный адаптер к существующему каналу, не инструмент воркера. **Наблюдатель** — только узкие проверки и карточки инцидентов; без доступа на выкладку, без claim и без LLM на каждом сообщении.

## 2. Состояние, данные и гарантии

### 2.1. Одна очередь и журнал эффектов

**Board — единственный источник очереди**, зависимостей `needs`, ownership, `ready/claimed/blocked/completed`. Стадия испытания, причина и квитанции видны в этой же карточке. Не вводить нативно несуществующие статусы, не держать другую таблицу приоритетов и не выдавать треды BB за бэклог. `claimed` допускает фазы запуска, исполнения, исправления и приёмки. `blocked` — видимый стоп, а не метка каждого красного теста.

**Локальный журнал** — только связь и эффекты, которых Board не знает: `task/epoch ↔ BB thread/worktree`, `intent → receipt/unknown`, ссылки и хэши доказательств. Для P0 один контроллер, один слот, имеющиеся JSONL-квитанции + один атомарный файл активной попытки и блокировка процесса. Не вводить SQLite второй очереди или распределённый broker на старте. Хранить журнал вне worktree, каталог `0700`, файлы `0600`, запись через временный файл/rename и fsync там, где она защищает внешний эффект. Возвращаться к транзакционному хранилищу только если пилот выявит необходимость нескольких независимых писателей. Токен native claim — секрет контроллера, не поле карточки, вывода, промпта или сдачи.

### 2.2. Минимальные контракты

| Запись | Что обязательно | Кто пишет / проверяет |
|---|---|---|
| Карточка и доверенный маршрут | `task_id`, approved channel/owner, repo и согласованная база, scope/spec ref с digest, `finish=verified|deployed`, `profile_id+version`, DoD, зависимости. Для `deployed` — допустимая цель и требования policy | Лид/оператор задаёт границы; контроллер проверяет allowlist и фиксирует неизменяемый scope попытки. Метка маршрутизирует, но не выдаёт разрешение |
| Привязка попытки | `task_id`, `epoch`, `attempt_id`, фактический `until`, `bb_project/env/thread`, worktree и `base_sha`. Отдельные `spawn_intent` и `spawn_receipt` | Только контроллер. Не считать `title` идентичностью треда. Не перезаписывать связь при повторном запуске |

### 2.3. Как работает один claim

1. Контроллер видит только доверенные готовые карточки. Один `claimReady`, записать намерение и ответ. Использовать выданный **фактический** `until`, а не предположение «lease час». Продлевать в рамках живой зарегистрированной попытки до истечения; проверять актуальность перед внешними действиями и приёмкой. Нативный epoch — последняя защита от позднего `complete`.
2. Запуск BB — внешний эффект. Записать `spawn_intent` до вызова; привязать `attempt_id` к проверяемому исходному сообщению, точному environment и проекту; подтверждённый ID записать после ответа. У `bb thread spawn` не найден клиентский ключ идемпотентности. Если процесс умер после отправки, **не обещать exactly once**: сверить наблюдаемый BB по полному совпадению запуска. Однозначный найденный тред подхватить; неизвестный исход — видимый стоп без второго spawn. Проверить это намеренной потерей ответа.
3. Сдачу принимать под **этим** claim. Нельзя `release → claim` ради совместимости со старым `accept()`: старый epoch больше не авторизует ту же работу. Дрейф содержимого, лишние untracked входы, mismatch SHA/profile/thread/epoch — отказ до следующего эффекта. Проверки делают `git`-снимок SHA и офлайн-профиль; условие чистоты перепроверяется перед финальной записью.
4. При доказанном исправимом дефекте сохранить тот же действующий claim. Отправить назначенному треду один `feedback_id` с командой, expected/actual и доказательством, без участия LLM-диспетчера. Перед `bb tell` журналировать intent; если ответ неопределён — сверять конкретное BB сообщение/очередь по маркеру, не повторять вслепую. Следующая проверка — новый SHA; повтор той же сдачи выдаёт уже записанный исход. Нет прогресса или требуется расширить scope — понятный стоп; не вводить произвольный универсальный лимит раундов.
5. При потере lease запретить все поздние сдачи и внешние действия старого epoch. Не выдавать другому тот же worktree, пока прошлый BB реально может писать (включая его фоновые задачи). При неясности один слот замораживается до сверки, а не стартует второй воркер. Любой автоматический стоп чужого процесса допустим только по явно разрешённой политике. Смена spec/risk/target также требует нового согласованного запуска.
6. Человеческая развилка исключительна. Нативный `block` завершает claim. После подтверждённого ответа контроллер снимает блок и получает новый epoch. Сохраняет контекст вопроса; старый worktree/тред можно продолжить только без старого активного писателя и с новым конвертом попытки. После approval для уже проверенного артефакта не запускать нового кодера: режим возобновления — выпуск. Повтор ответа не делает второго `unblock` или `spawn`.

### 2.4. Политика выпуска (проектные запреты не смягчаются)

- Отдельно `проверен` и `развёрнут`. Любая цель выпуска связывает согласованный SHA с неизменяемым digest, фиксирует целевое окружение, действующие branch checks и предыдущую известную версию. Если итоговый merge SHA отличается — проверяется фактический код/артефакт, который будет выпущен. Нельзя приписать старую проверку новому бинарнику.
- Риск и допустимый путь выбираются **до исполнения** из реально действующих правил проекта. Для harm10 merge/push/prod сохраняется owner gate. Триггеры GitHub Actions сами по себе не включаем. Запрещены прямой коммит или push в защищённую ветку и обход required checks. Миграции, оценки/данные, CI/PR и секреты остаются под действующими разрешениями.
- Если действие не разрешено, ноль side effects и один точный запрос. Не считать текст `да` или `--as owner` доказательством полномочия: профиль на том же UID отделяет имена, не власть. P1 должен подключить реально проверяемый операторский канал/раздельные полномочия; пока это не доказано, production release выключен. Смена SHA, digest, цели, политики или плана отката обесценивает прежнее разрешение.
- Release-адаптер переиспользует согласованный канал, не запускает старый `factory/train.py`. Идемпотентный ключ продвижения — действие+target+digest. Завершение только после проверки фактически работающей версии **и** базового сценария на цели. Перед командой — intent; при пропаже ответа сверить состояние канала и целевую версию. Повтор вслепую запрещён даже при сохранённом разрешении. При красном smoke — только заранее разрешённый откат к доказанной предыдущей версии с повторным smoke; иначе явная эскалация. Нет молчаливого восстановления БД.

## 3. Где изменится код

| Модуль | Изменение и граница |
|---|---|
| `board_pipeline/acceptance.mjs`, `submit.mjs` | Один механизм тестов/ревью/seal. Новый вход `acceptHeld(attemptRef, candidateSha)` не вызывает `claim`; возвращает `verified`/`rework`/`hold` с receipt. Операторский `submit` сохраняется как совместимый ручной путь v1; не копировать приёмку |
| `board_pipeline/native-board.mjs` | Изолировать claim/renew/held/release/settle. Native `ready`, реальный `epoch/until`; контроллер не подменяет Board и не опирается только на проекцию статуса одного события. Секреты только в доверенном состоянии процесса |
| Новый небольшой контроллер в `board_pipeline/` | Узкий pull/claim, один активный слот, записанный intent, привязка запуска BB и восстановление, сдача/возврат, состояние и один вопрос. Начать foreground, не устанавливать демона на живую Board до доказательства. Пользовательский view — та же карточка |
| `runtime.mjs`, существующий `board-review.mjs` | Повторно использовать точный Git snapshot и локальный runner. Квитанция ревью в v2 привязана к зарегистрированной попытке/версии политики; повторный старый checkpoint не выдаётся за новый ход. Тестовый URL, путь к журналу и область ревью изолированы **обеими** сторонами; актуальный установленный gateway не переписывать для пилота без отдельного решения |
| Approval/release, только P1 | Один вход вопрос/ответ (реальный проверенный оператор), один адаптер существующего канала, smoke и подтверждённый rollback. Не передавать команду на деплой через произвольный worker text и не вводить вторую очередь |

Включение автоматического маршрута — allowlist `repo / channel / owner / profile / finish`, выключение снимает только автоматический захват, без потери текущих карточек. Не включаем широкие watcher-триггеры, Eve, дополнительный трекер, новый облачный сервис или LLM-агента для пустых тиков. `factory/book.py`, старый диспетчер, архив, правила БГУ/Tracker и их текущие worktree не мигрируем в ходе пилота.

## 4. Порядок реализации и тикеты

Один worktree на самостоятельный результат, а не на каждую строку в этой таблице. Приёмка и контроллер трогают общие файлы — последовательные изменения одним владельцем, независимое ревью отдельно. Малый настоящий сценарий важнее параллельного разрастания. Это заготовки для Board, реальные карточки и исполнения в этом ходе не создавались.

| Тикет | Что сделать | Depends on | Проверяемый выход |
| --- | --- | --- | --- |
| **P0.0. Стенд и доверенный маршрут** | Утвердить базу, изолированные Board/журнал/ревью, один локальный fixture-project и реальный BB preset. \[VERIFY\] `claim/held/renew`, чтение конкретного launch/turn/queued reply в данном BB; подтверждённое место хранения и capability scope. \[MEASURE\] диск, время/стоимость одного прогона | — | Реплей событий на тестовой Board; публичная команда smoke и ограничения. Никакого подключения распространённых каналов |

## 5. Приёмка: что должно стать красным при плохой реализации

| Проверяемый случай | Доказательство |
|---|---|
| Неавторизованный канал/актор/метка, `waiting` и пустая очередь | 0 запусков; никакого LLM для определения готовности из текста |
| Дубли ready / concurrent tick / процесс прерван до и после spawn | В первом случае максимум один определённый BB; при потерянном ответе сверка или один наблюдаемый stop. Не подделывать «exactly once» простым `retry --until-green` |
| Lease истёк, BB ещё жив; перезапуск Board/контроллера | Поздняя сдача отвергнута до исполнения; никто параллельно не пишет в worktree. Состояние прочитано из native claim + BB, не только из старого `claimed` или из отсутствия событий |
| Красный тест; отдельный `REVIEW_BLOCKED`; пересдача | Красный тест не запускает review; review-блок цитирует конкретный контрпример и checkpoint. Оба пути возвращаются ровно один раз. Новый SHA проходит проверку; тот же SHA/phase не повторяется |
| Ошибка стенда, нехватка места, отказ в разрешении | Не блокируется как «исправь код» и не обходится повышением прав. Карточка показывает точную причину и следующий ход |
| Вопрос владельцу, повтор тика, повтор/подмена ответа | Один вопрос; только подтверждённый ответ на этот scope/target продолжает. Для выпуска новый SHA/resources/цель требуют пересмотра, а не используют старое «да» |
| Выпуск: без разрешения, с разрешением, сбой после команды | Без разрешения ноль внешнего действия. С разрешением — один доказанный эффект на target+digest; после потери ответа сначала read-back фактического состояния. Красная проверка даёт разрешённый откат либо честный стоп |
| Жалоба после выпуска наблюдателем | Есть воспроизводимый факт с текущей версией, повтор не создаёт второй инцидент; никак не расширяет разрешение |

**Прогоны.** Тесты интерфейсов и таблицы отказов (`node --test board_pipeline/*.test.mjs`) → интеграция с отдельным `vb serve` и заглушками для crash windows → реальный BB/независимый gate на одной синтетической задаче. Не путать успешную заглушку с E2E. Искусственно воспроизводим красный сценарий тестовым артефактом/реальным тестом, не просим ревьюера выдать фиктивный блок. Для P1 — реальный side effect только на разрешённой изолированной цели, подтверждённая версия после и останов процесса/очереди после прогона. Старый `submit` и исходный пилот остаются регрессией. Релевантные проектные наборы — на финальном SHA согласованного профиля, не полный прогон после каждой пробы.

**Метрики.** 0 ручных переходов от доверенной ready до результата или нужного решения владельца; 0 повторных спавнов/выкладок для одной подтверждённой попытки/цели; 0 model turns в простое. Сохраняем время ready→проверка→кандидат→выпуск и число вызовов/пересдач; объём и стоимость — по фактическому usage, не по количеству Board-событий. Эскалация показывает причину, следующее действие и человека, способного его сделать.
