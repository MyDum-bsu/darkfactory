# VS-2 T4: согласованный выпуск на изолированную цель

`finish=deployed` в этом срезе означает переключение статического артефакта на отдельно зарегистрированной loopback-цели. Код кандидата не исполняется. Нет PR, push, CI, production или выпуска на `:44100`. Операторский pilot-маршрут остаётся `verified`-only. Без настроенного ReleasePort прежний изолированный T2 останавливается на `release_ready` и не выпускает.

## Цель и политика

Оператор отдельно создаёт приватный канонический каталог (0700) вне worktree, каталога сдачи и state. Из доверенного локального процесса один раз вызывает `enrollLocalTarget(directory, { target, repo, initialSha, initialBytes })` из `board_pipeline/release-target.mjs`; `initialBytes` — байты известной рабочей версии, не сдача кандидата. Эта операция не вызывается фабрикой. В том же модуле `serveLocalTarget({ root: directory, target, repo, port })` запускает read-only сервер на `127.0.0.1`, отдающий свой точный `url`. Например, тест-контур вызывает его с `port: 0`; рабочий порт `44100` запрещён.

Фрагмент **доверенной изолированной** политики (URL — реальный URL этой тестовой цели, другой порт, чем у Board):

```json
{
  "scope": "isolated",
  "channel": "pilot",
  "route": { "finish": "deployed", "repoId": "fixture-repo" },
  "release": {
    "enabled": true,
    "directory": "/operator/isolated-release-target",
    "target": "isolated-t4",
    "url": "http://127.0.0.1:44981",
    "artifact": "release.txt",
    "smokePrefix": "READY\n"
  }
}
```

Обязателен зарегистрированный `questionGate`, маршрут из очереди (без `taskId`) и фактический fingerprint всех операторских входов, без ручного `policyDigest`. `artifact` — относительный путь к обычному tracked blob `100644` в точном SHA кандидата. Только UTF-8, до 512 КиБ; симлинки и скрытые команды не поддерживаются. `smokePrefix` — заранее утверждённый контракт поведения статической цели в этом срезе, а не параметр от воркера. Он отделён от проверки SHA-256 байтов: правильно идентифицированная версия может провалить smoke.

## Подпись и фактический выпуск

1. `prepare` читает blob, фактическую предыдущую версию и её smoke. До L1/L2/L3 в `CandidateSubject` закрепляются цель, канал и предыдущий digest. После зелёного seal фабрика публикует один `QuestionEnvelope` с `consequence`, точным SHA/digest, `subject_digest`, предыдущей версией и digest всего пакета (включая экземпляр цели, smoke и условие отката).
2. Владелец проверяет поля и подписывает весь `QuestionEnvelope` с `decision: approve` и пустым `answer` по [каналу T2](vs2-t2-owner-answer.md). Продвижение требует `ApprovalReceipt` уровня `harm=10`, новую нативную эпоху, делается без запуска или пробуждения кодера. Чужая, просроченная или подписанная для другого пакета квитанция не даёт выпуска. Перед записью ещё раз сверяются доверенные входы, корень worktree, точный SHA, версия цели и живая аренда.
3. `ReleasePort` под `flock` резервирует однократный ключ `action + target + artifact digest`, сохраняет проверенные предыдущие байты как rollback-пакет и атомарно переключает `live.json`. Сервер одновременно читает snapshot активных байтов, отвечает `/version` и отдаёт `/artifact`, не кэшируя их. Контроллер проверяет тот же SHA/digest и ID операции на цели и проверяет дымовой сценарий по фактически отданным байтам. Зелёный результат даёт один нативный `complete` с привязанным `ReleaseReceipt` (`finish=deployed`).
4. Доказанный красный smoke разрешает только подписанный откат: под тем же lock сверяется текущий кандидат и его ID операции, затем восстанавливаются закреплённые предыдущие байты. Статус и smoke предыдущего обслуживаемого артефакта проверяются снова. Задача остаётся `blocked`, не `deployed`. Если версия изменилась, smoke не наблюдаем или старый checkpoint больше не держит эпоху, это `uncertain`, а не разрешение на запись.

Намерения promote, rollback и нативного settle пишутся до эффекта. После обрыва подтверждение получают по фактическому read-back той же операции или нативной карточки. Повтор публикации, отката или нативного закрытия вслепую запрещён. Истечение допуска до publish останавливает выпуск; после начатого выпуска применяется уже подписанный откат только к тому же пакету и под живой эпохой. Нужна ручная сверка, если право истекло или состояние нельзя доказать.

После подтверждённого выпуска [наблюдатель P2.2](p22-release-watch.md) может отдельно проверить HTTP smoke той же версии и передать инцидент во вход лида. Он не получает прав выпуска или отката.

Приёмка: `npm run test:tla`, `npm test`, `npm run test:integration`. Трассы поднимают реальную временную Board и отдельную HTTP-цель, проверяют реальную смену управляемых байтов, отказ без подписи, потерю подтверждений и restore после красного smoke. Это не разрешение на боевой выпуск.
